Why I Rewrote My Personal Site from Nuxt, Supabase, and Tailwind to the HCJ (HTML, CSS, JavaScript) Stack

By Pramudita Ahmad

I think I first got to know web development around 2014. Back then, I was just a kid who wanted to build something on the internet.

I started with HTML. Honestly, I just wanted to display an image on a webpage. Sounds simple, right? Well, not for me at that time. I struggled just to get an image displayed correctly. But I guess that's understandable — I was only around 11 years old.

During that period, I also tried Bootstrap for the first time. I didn't really understand how to use it, and I don't think I successfully built anything with it either. But there was one thing I noticed: there were so many technologies available for building websites.

I didn't know it yet, but that was probably the beginning of my curiosity about web development.

Getting Started with My First Personal Site

Fast forward to around 2021, I started developing my first personal site.

I remember watching tutorials by Sandhika Galih on YouTube. His approach introduced me to building websites using HTML, Bootstrap, and even integrating a contact form with Google Sheets. It was a simple setup, but it was enough to make me realize that I could build something useful with just a few technologies.

That was also when I started taking web development more seriously.

I began exploring more things, starting with CSS and eventually moving to utility-first CSS frameworks like Tailwind CSS. I found styling websites surprisingly enjoyable. There was something satisfying about turning a plain HTML structure into an actual interface. And honestly, I think that's where my interest in frontend development really started to grow.

Exploring the Web Development Ecosystem

As I continued learning, I started exploring different technologies used in web development.

One of the first programming languages I encountered specifically for the web was PHP. Well, I have to admit, PHP was never really my favorite language at first. But it was part of the learning process, and I learned quite a bit from working with it.

At that point, I realized that web development was much bigger than just writing HTML and CSS. There were frontend frameworks, backend languages, databases, state management, APIs, and so many other things to explore.

Btw, my first experience with a modern frontend stack was React with Redux. And yeah, it was really difficult for me lol. There were so many concepts to understand, and managing state with Redux felt overwhelming at the time.

Then, one of my teachers suggested that I try Vue instead.

And I fell in love with it, thanks god i really love vue.

I found Vue much more comfortable to work with. Its approach to components, templates, and reactivity made sense to me. I started building quite a few prototypes using Vue and Tailwind CSS. It was a fun period because I could focus more on building interfaces and experimenting with ideas instead of constantly struggling with the tools.

I Needed a Backend +_+

Eventually, I started building applications that required more than just a frontend. I needed dynamic data, database integration, authentication, and other backend capabilities.

Since I was studying Software Engineering at a vocational high school (SMK), I was introduced to Supabase as a Backend-as-a-Service (BaaS). At that time, Supabase was becoming quite popular, especially because it used PostgreSQL as its underlying database.

That was particularly interesting to me because I was already familiar with relational databases and SQL. Before that, Firebase was another popular option I had encountered, but its document-oriented NoSQL approach felt less familiar compared to working with relational databases.

Supabase felt like a natural fit. It allowed me to work with PostgreSQL without having to build and manage an entire backend from scratch. From there, my projects became more ambitious, and I started exploring more technologies and architectural approaches.

Building My Seriously Personal Site

After learning Vue and exploring backend technologies, I eventually started building a more complete version of my personal site.

At this point, I wanted something more than just a simple webpage with my name and a list of projects. I wanted a digital home where I could introduce myself, showcase my work, share my thoughts, and give people a better understanding of who I am as a developer.

The personal site was built using Nuxt, Tailwind CSS, and Supabase, along with some JavaScript utility libraries.

I chose Nuxt because I was already comfortable with Vue, and Nuxt provided a structured way to build a full-featured website. Tailwind CSS helped me develop the interface faster, while Supabase handled the data and backend-related features.

The website was designed around several main sections:

  • Hero Section: The first thing visitors see when opening the website. It introduces me, gives a brief overview of what I do, and provides a starting point for exploring the rest of the site.
  • About Me: A place where I share more about myself, my background, interests, and my journey in software engineering.
  • Projects: A collection of projects I've worked on, including descriptions, tech stacks, and relevant details.
  • Blog: A space where I write about technical experiences, things I've learned, personal opinions, and random thoughts related to software engineering.
  • Contact: A section containing ways to reach me through email and social media.
  • My Music: A little personal touch displaying some of my favorite tracks. I think a personal site doesn't always have to be strictly professional — adding something personal makes it feel more like me.
"I can do anything I want, it's my personal site loller."

Why Did I Choose Supabase

One of the interesting parts of this project was how I managed its content. Since I wanted the personal site to be dynamic, I needed a way to manage project information, blog posts, and other content without manually changing the frontend code every time.

I used Supabase as the backend, with PostgreSQL as the database. Instead of hardcoding everything into the frontend, I could store and retrieve content dynamically.

At that time, it felt like a reasonable architectural decision. Connecting Nuxt to Supabase also gave me an opportunity to explore database integration, API requests, and the relationship between frontend and backend systems. So, it wasn't just about making my personal site work — it was also a learning experience.

But Do I Really Need All of That?

After using this setup for a while, I started looking at the project from a different perspective.

The personal site was working fine, and I had no major technical complaints about Nuxt or Supabase. The problem was more about whether the architecture still made sense for the actual needs of the website.

Think about how often I update my personal site. Maybe once every two months, and usually just to add one new project. The blog is also something I update occasionally rather than every day. My music section doesn't require frequent changes either. And for the contact section, most people who want to reach me usually contact me directly through social media anyway.

So, I started questioning the value of maintaining a database and a CMS-like workflow for such a small amount of relatively static information. Was I actually solving a problem, or was I just maintaining a system that I didn't really need?

The Hidden Cost of Keeping Things Dynamic

Another thing I started considering was the operational cost and dependency.

Supabase offers a generous free tier, which is great for personal projects. However, free services still come with usage quotas, resource limitations, and project inactivity policies that pause your database if there's no traffic for a while. I didn't particularly like having an external service dependency just to display a few project entries and blog posts.

On the other hand, what if I hosted my own backend and database on a VPS? Let's assume I rent a small VPS for around IDR 150,000 per month. It might seem affordable at first, but the cost adds up over time:

Period Estimated Cost
1 month IDR 150,000
1 year IDR 1,800,000
2 years IDR 3,600,000
3 years IDR 5,400,000

Note: These figures are estimates based on a fixed monthly VPS cost of IDR 150,000, excluding domain registration, backups, and other operational expenses.

Spending IDR 5.4 million over three years — plus handling server monitoring, security updates, and backups — just to keep a personal site alive feels excessive. I enjoy infrastructure and Linux system administration, but enjoying something doesn't mean I should force it into every project.

What Programming in C Taught Me About Web Bloat

There was another major turning point that shifted my perspective on software architecture.

Outside of web development, I started spending a lot of time programming in C and exploring systems programming across both Windows and Linux. I built native desktop applications, wrote a lightweight relational database client from scratch, and even created a CLI-based music player.

Working with C changes the way you look at software. When you build native applications or CLI tools in C, you become hyper-aware of memory, dependencies, and what the machine is actually doing under the hood. Your program compiles into a tiny, fast binary that does exactly what it needs to do — nothing more, nothing less.

Then I looked back at my personal site.

To render a few pages of text, links, and images, I was relying on a massive node_modules folder, a full reactive JavaScript framework, a CSS build pipeline, and remote API calls to a cloud PostgreSQL database. After experiencing the raw simplicity and efficiency of native C programs on Linux and Windows, my web stack suddenly felt unnecessarily bloated.

I realized I wanted my personal site to reflect that same philosophy: close to the metal of the browser, zero unnecessary abstractions, and completely self-contained.

Do I Really Need a CMS?

When I looked closely at my workflow, the contrast became even clearer.

With a dynamic CMS-based approach, I had to maintain:

  • The content management interface.
  • The PostgreSQL database and its schema.
  • The connection and environment variables between Nuxt and Supabase.
  • API requests, loading states, and error handling.
  • External service availability.
  • Build and deployment configurations.

With a static approach using the HCJ (HTML, CSS, JavaScript) stack, the workflow is stripped down to the essentials:

  1. Edit the HTML file.
  2. Commit the changes to Git.
  3. Push and deploy.

That's it. I also get version control for free through Git. Every content update becomes part of the repository history, allowing me to track modifications and roll back changes effortlessly.

For contact, simple direct links to my LinkedIn, GitHub, and email accomplish the exact same goal as a backend-powered contact form without any of the complexity. And for the blog and music sections, static files are more than enough for content that only changes occasionally.

Back to the HCJ (HTML, CSS, JavaScript) Stack

After considering all of that, I decided to rewrite my entire personal site using plain HTML, CSS, and JavaScript. No Nuxt. No Tailwind build step. No Supabase. No database. Just the fundamentals of the web.

This wasn't because I suddenly disliked modern frameworks. I still use them for complex applications where they provide real value. But for my personal site, I wanted radical simplicity.

For hosting, I can simply use static hosting platforms like GitHub Pages or Cloudflare Pages at zero cost, with near-instant load times and zero database cold starts.

The result is a much cleaner architecture:

  • No database or backend infrastructure to maintain.
  • Zero external runtime dependencies or build-step headaches.
  • No CMS to manage.
  • A frictionless Git-based deployment workflow.
  • Zero operational cost.

Most importantly, I can spend my time building actual software — whether that's full-stack web apps or native tools in C — instead of maintaining the infrastructure behind a personal site that rarely changes.

Engineering Is Not About Using as Many Technologies as Possible

Being a software engineer isn't about always using the latest technology, chasing the most popular framework, or building the most sophisticated architecture possible. It's about understanding the problem, respecting the platform, and choosing an appropriate solution.

There is a big difference between building something because we need it and building something simply because we can.

In my case, moving from Nuxt, Tailwind, and Supabase back to plain HTML, CSS, and JavaScript wasn't a step backward or a limitation. It was a conscious engineering decision. Sometimes, the best engineering decision isn't adding another technology — it's knowing when to strip them away.

Looking Back

It's funny to think about how everything comes full circle.

Back in 2014, I was just an 11-year-old kid struggling to display an image using HTML. Now, after years of exploring full-stack frameworks, cloud databases, and low-level programming in C, I find myself appreciating the raw fundamentals of the web even more.

Learning modern frameworks wasn't a waste of time — those experiences taught me why and when certain abstractions are useful. And sometimes, going back to where you started isn't going backward at all. It's moving forward with clarity.
